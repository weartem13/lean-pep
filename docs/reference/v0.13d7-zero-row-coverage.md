## The representation gap

The current Lean profile includes every ordered pair, including self-pairs.
PEPit's Function.add_constraints_from_two_lists_of_points instead places a
numeric zero in its diagnostic table for identical sample tuples, without
appending a scalar Constraint to list_of_class_constraints. This behavior was
checked in the upstream primary source on 25 September 2026:
https://raw.githubusercontent.com/PerformanceEstimation/PEPit/master/PEPit/function.py

D7 addresses only that missing-zero-row representation gap. The delivered
artifacts are deterministic exact fixtures, NOT captures from a live solver or
an installed PEPit run. No PEPit package is needed for regeneration or tests.

For actual steps T=n+1>0 the complete D6 family contains

  (T+2)^2 + (T+1)^2 + 2

rows (both component grids, radius, and the auxiliary performance row).
Omitting all self-pairs removes 2T+3 identically zero rows and leaves

  (T+2)(T+1) + T(T+1) + 2.

The one/two/three-step fixtures thus have 10/20/34 rows instead of 15/27/43.
A fourth fixture retains all 15 one-step rows, including zero rows. Partial
retention of zero rows is also supported; compaction is not mandatory.

## Exact coverage, not a missing-row repair heuristic

The generic ZeroRowCoverage.MapQ k r submits BOTH arrays:

  toFull   : Fin k -> Fin r
  fromFull : Fin r -> Option (Fin k).

The first maps compact storage indices to full D6 SOURCE storage indices.
It is not a map directly to the final canonical profile order. `none` marks
an omitted full row. The two checks establish

  fromFull (toFull i) = some i;
  fromFull j = some i -> toFull i = j.

They imply injectivity of toFull and that `none` is exactly the complement of
its image. There is no false bijection claim between different cardinalities.
The core handles k=0 and/or r=0; an empty actual PG source cannot pass because
its nonzero performance/radius rows could not be covered.

Every retained RAW expression is compared to its mapped complete expression.
Every absent complete expression must be identically zero in ALL rational
coefficients: constant, every scalar value, and every Gram entry, including
both off-diagonal axes. Tests at a primal witness, small floating residuals,
zero dual weights, skew-symmetric cancellation, or vanishing after setting
an origin/tau variable do NOT meet this criterion.

The PG adapter additionally compares retained direction/scale rules and logical
row labels with the mapped full rules/labels. Equal zero polynomials do not
license exchanging distinct logical labels or changing a row's declared rule.

## Input and template trust boundary

The input contains a D5 base_source template, a performance rule, the coverage
arrays, actual compact raw rows/rules/labels, the auxiliary objective, and ONE
sparse upper certificate. There is no input full/base upper certificate.

completedSourceQ creates the D6 full extended row family using D6.expectedRowsQ
on the submitted base template. This template is not trusted: D6/D5/D4/D3/D2
source checks independently bind it to the original Lean profile. Actual
compact rows are compared BEFORE completion to that proposed family, and
omitted full rows are explicitly checked to be zero. This is checked completion,
not replacing the actual submitted compact model before auditing it.

The compact model's assumptions are precisely List.ofFn of the submitted raw
rows after applying their submitted directions. The primal/dual local checker
therefore sees the actual shorter constraint list.

The JSON carrier reuses D5 source validation with a private zero-upper parsing
scaffold. That scaffold is not an input proof, is not rendered, and is never
used as the submitted sparse or completed certificate. Rendering produces the
base source and actual compact data, with one literal sparse upper declaration;
it emits no acceptance theorem. Fin coverage entries are bounded constructors,
not modulo-style out-of-range numeric recovery.

As in prior versions, Lean audits the generated typed data, not the original
JSON parser's byte semantics, producer identity, or provenance hashes.

## New mathematical statements

ZeroRowCoverage.feasible_iff proves pointwise equivalence of all compact and
full inequalities for ANY real data (no PSD, symmetry, or realizability).
ZeroRowCoverage.finite_upper_equivalence adds the same unchanged PSD condition
and objective to both sides. It equates ALL scalar upper-bound statements,
without assuming attainment, nonempty feasible sets, a known rate, or duality.

In the PG adapter, oriented_coverage_check and rows_feasible_iff apply the
same reasoning with submitted directions. They happen BEFORE D6 substitutes
tau=metric and BEFORE D3 removes the origin coordinate. The nonzero link row
cannot be omitted merely because its later substitution is zero.

The compact certificate's reference i is mapped to toFull i. This completion
keeps every supplied term, weight, zero weight, repeated reference, and term
list order. It does not append artificial multipliers for the absent zero rows.
Bound, objective, dual matrix, factors, and implicit interpolation list remain
byte-for-byte values of the original submitted certificate.

assumption_sum_preserved proves equality of complete LinearExprQ sums, not
just equality of one numerical evaluation. certificate_rhs_preserved and
completedUpper_check use that identity and the unchanged checker
soundness/completeness. Implicit interpolation is explicitly required empty;
the auxiliary scalar is not a smooth-function sample. D7 preserves the list
rather than removing it to make downstream checking pass.

checkBoundQ retains both original compact certificate checking and the D6
joint checking of the completed candidate, plus source, objective, and empty
implicit guards. checked_certificate transports the SAME bound into the old
canonical profile. The actual-function wrapper calls D6 unchanged. It proves
LR^2*c.bound with the original function, minimizer, run, and radius assumptions.
The concrete three-step application remains LR^2/12, not a new rate/tightness.

## Counterexamples and limits of rejection

The strongest regression deletes an UNUSED NONZERO source row. Both the local
compact certificate and its completed certificate still accept, but the D7
coverage audit rejects the missing nonzero row. Such deletion relaxes a problem,
so a valid upper bound for the relaxed problem may still be sound for the old
problem. D7's rejection is about the exact formulation-equivalence contract,
NOT proof that this candidate bound or the optimization theorem is false.

Other checks include partial inverse corruption despite a correct completed
source, swapped labels on two zero rows, hidden tau pollution before substitution,
performance/radius omission, zero weights, repeated performance references at a
moved compact row, malformed sizes, duplicate JSON keys, and wrong objectives.

The fixture creator is a separate explicit operation. When constructing new
compact fixtures from a prior full certificate, it may remove references to
omitted ZERO polynomials. This is not what the importer does: the importer
never discards a term of the actual submitted compact certificate.

## CLI

  python3 tools/import_proximal_gradient_sparse.py \
    data/fixtures/composite_sparse/pg_three.json \
    --expected-steps 3 \
    --lean /tmp/PGSparseThree.lean \
    --report /tmp/PGSparseThree_report.json \
    --completed-json /tmp/PGSparseThree_completed.json \
    --namespace LeanPEP.Imported.PGSparseThree

The importer accepts only the exact num/den schema. In-range mathematically
bad maps may be rendered for independent Lean rejection. It never infers an
inverse, label, missing nonzero expression, direction, ratio, or certificate.
Completion export is BLOCKED unless source coverage and full source binding
pass. This prevents a missing-nonzero-row candidate from being laundered into
an independently valid D6 artifact which no longer records its omission.

Successful completion may be passed through unchanged D6, D5, D4, D3, D2 tools.
Every report explicitly keeps lean_checked=false until Lean is actually run.
The default regeneration reads committed sparse inputs only. Fixture creation
requires the explicit --create-fixtures option.

## Not included

No live capture; automatic row/leaf matching; arbitrary extra or redundant
nonzero rows; equalities; incomplete active-set models; new auxiliary layouts;
floating reconstruction; raw-byte/producer authentication; native primal
transport; interpolation completeness; or a completed end-to-end solver chain.
The full D5 source template remains required, so this is not a compressed
serialization of every source field or a claim to minimize file size.
