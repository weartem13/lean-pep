## What changes mathematically

D10 solves the exact coefficient equations A x = b while keeping each free
variable at its seed value. That is only an affine solve: a negative free
multiplier remains negative even when another nonnegative solution exists.
D11 searches the affine space subject to finite rational lower and upper bounds.
It does not clip input values and does not simply project a vector onto a box.

The variables are bound followed by ALL existing assumption weights. The
unchanged D10 compiler retains the constant coefficient, every value coefficient
(including tau) and both axes of all Gram coefficients. It freezes the D8 SEED
objective, independent residual, factors and references, not the RAW matrix.
No new certificate checker or algorithm-specific upper-bound logic is introduced.

For the declared raw-to-final absolute error budget eta:

    bound in [raw_bound - eta, raw_bound + eta]
    weight[j] in [max(0, raw_weight[j] - eta), raw_weight[j] + eta].

In particular the bound coordinate has no artificial positivity requirement.
The intervals are centered on RAW, never on seed or on D10's previous attempt.
Empty intervals are valid infeasibility inputs, not silently widened intervals.
`policy_interval_iff` and `policy_box_iff` give the exact algebraic connection
between these intervals, nonnegativity and absolute error in the Lean scripts.

## Exact search and independent verification

`tools/solve_exact_box_system.py` is a generic exact rational phase-I simplex
feasibility search. It translates x=l+z, introduces upper-bound slacks and
equality artificial variables, and uses least-index entering variables with
Bland tie-breaking among minimum-ratio leaving variables. All arithmetic and
comparisons use `Fraction`; no floating solver, tolerance or PSD projection is
used in production. The scalar phase-I objective is not the PEP bound.

The implementation and termination are not formally verified. It returns:

* `feasible`: a rational point rechecked against every ORIGINAL equality and bound;
* `infeasible`: an independently checked rational Farkas obstruction;
* `limit`: the pivot budget was exhausted; no mathematical conclusion is claimed.

An already feasible D10 candidate is retained. Otherwise free variables may move.
This is not nearest-point computation or optimization of the PEP bound.

## Farkas witness semantics

An obstruction has unrestricted equality multipliers y and nonnegative lower
and upper multipliers nu,mu, satisfying

    A^T y + mu - nu = 0,
    y^T b + mu^T u - nu^T l < 0.

For any feasible x the second expression would equal

    sum_j nu[j] * (x[j]-l[j]) + mu[j] * (u[j]-x[j]) >= 0,

a contradiction. `RationalBoxSystem.margin_eq_slacks`,
`obstruction_not_feasible`, and `checked_obstruction` implement this argument
for arbitrary finite rational systems, including zero rows/columns and empty
intervals. The witness is transported back to ORIGINAL equalities and bounds,
not merely checked against a transformed tableau.

This proves no RATIONAL point exists for the supplied system and box. The
Python source-to-system compiler is still not verified in Lean: the negative
result is not advertised as a theorem about every certificate of the PEP.
It is not general PEP infeasibility and says nothing about other residuals or
larger error budgets. The positive theorem does not trust this compiler at all:
the unchanged D10/D9/D8/... checker independently audits the final certificate.

## Denominator limits remain a separate constraint

The finite denominator cap M is not encoded by rational linear inequalities.
The search can find a feasible rational point whose denominator exceeds M.
The unchanged final policy check must reject such a candidate. This does NOT
prove absence of another point with admissible denominators. D11 does not
search that discrete restriction or promise recovery whenever such a point exists.
A Lean regression shows 3x=1 is box-feasible but denominator cap 2 rejects 1/3.

## Endpoints and unchanged trusted path

The output retains the original capture, raw, seed, the old D10 free-seed
attempt, the optional bounded candidate, the entire box system and its witness,
and separate reports. Neither raw nor seed becomes accepted retroactively.

The final positive check is exactly the EXISTING
`ProximalGradientCompletion.checkCompletedQ`, including seed policy, frozen
objective/residual/factors/references, final raw-to-completed policy, trace
binding, source audit, exact identity, multiplier signs and PSD checks. A box
solution is not a replacement for any of these checks. Concrete vector-binding
proofs additionally match generated coordinate vectors to bound/weight lists.

The new actual-function application calls the existing D10 theorem unchanged:

    (f+h)(x_T) - (f+h)(x_star) <= L R^2 * completed.bound.

No eta term is added because the final certificate itself must be exactly valid.
No new rate, tightness, automatic lower witness or solver optimality is claimed.

## Fixtures and their interpretation

The one-, two-, and three-step fixtures are explicitly `simulated_regression`.
They add one permitted retained zero smooth self-pair to a D10 simulation and
record its multiplier as -0.0001. The same input is passed to D10 and D11:
D10 keeps this free multiplier and is rejected; D11 finds a point with weight
zero in the original 0.001 budget. The row and reference are NOT deleted.
PEPit normally omits such self-pairs; these are protocol diagnostics, not live
PEPit captures or evidence about arbitrary nonzero-row degeneracy.

A separate, genuinely coupled generic example has x+y=1, box [0,1]^2 and the
D10-style affine point (2,-1). The new search returns (1,0).

The `budget` PEP fixture has a perfectly valid affine certificate at bound 1/4,
but raw bound 0.2531 and budget 0.001 prohibit it. Its box obstruction margin is
-21/10000. The generated negative replay proves only the submitted box has no
point and contains no positive actual-upper theorem.

## Commands

After applying the version patch:

```bash
lake build LeanPEP && lake env lean tests/lean/smoke/V13D11SmokeTest.lean
```

After the library builds, a separate generated replay can be checked:

```bash
python3 tools/complete_bounded_pepit_capture.py \
  data/fixtures/pepit_bounded/pg_three.json \
  --expected-steps 3 \
  --output-dir /tmp/pg-d11-three \
  --namespace LeanPEP.Imported.PGD11Replay \
  --require-completed-pass && \
lake env lean /tmp/pg-d11-three/Replay.lean
```

The output directory must not exist or must be empty. No user file is deleted.
A failed `--require-completed-pass` returns 2 after retaining diagnostics; bad
input returns 1. `--max-pivots 0` tests an unknown/limit outcome. No solver is
invoked by regeneration or by any committed regression.

## Tests and scope

New tests cover exact coupled feasibility, empty/degenerate systems, singleton
and empty intervals, tiny nonzero contradictions, witness corruption, strict
list sizes, deterministic pivoting, limits, retained negative zero-row weights,
raw budget binding, frozen residual and factors, simulated/live labeling,
independent source/checker rejection, and standalone CLI output. The generic
search is compared with independent exact vertex enumeration using SymPy.

No source-to-system compiler correctness, real-valued Farkas lifting, bounded-
denominator search completeness, residual search, live PEPit integration,
primal/interpolation completeness, or general nonlinear reconstruction is added.
