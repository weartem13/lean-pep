## Narrow supported problem

The producer builds unit proximal gradient with T>0, L=1, step=1 and squared
radius=1, using exactly `SmoothConvexFunction` and `ConvexFunction`, one final
composite gap, scalar inequalities, and no extra LMI, equality, inactive row,
additional function sample or dependent leaf. At x_star it gives the smooth
oracle g_star and the nonsmooth oracle -g_star. Neither component is separately
assumed stationary. At x0 it requests only the smooth oracle; h samples are
x_star,x1,...,xT. The final smooth oracle is explicitly queried.

The live script uses PEPit's actual `proximal_step`, class-constraint generation,
point/expression decomposition dictionaries and original leaf counters. It does
not import a certificate formula, load an accepted example, recompute a dual
matrix from multipliers, or insert a known 1/(4T) bound. Labels are associated
with actual constraint objects using the class-constraint tables. They are not
inferred by parsing a formatted inequality or used as substitutes for checking
all coefficients.

Before optional solution it calls the pinned `_prepare_constraints` API once.
After solution it requires the prepared and sent row-object lists to agree in
order. Every row has exactly one recorded dual, including exact/numerical zeros
and small negative values. The independent `problem.residual` is captured
entrywise. No threshold, symmetrization, PSD projection, clipping, dimension
reduction or active-set filtering is applied by the exporter to this residual.
The recorded bound is the value returned by PEPit with `return_primal_or_dual`
set to `dual`; it is not a newly manufactured certificate bound.

## Symbolic exactness versus numerical exact interpretation

Symbolic integer coefficients are exact integers. A Python binary float in an
actual symbolic decomposition is encoded as `Fraction.from_float` without a
small-denominator approximation. For the supported unit problem the relevant
source coefficients are dyadic. A symbolic term q*<vi,vj> is encoded by adding
q/2 to each transposed coefficient slot, including both halves on a diagonal.
That is a convention for compiling a symmetric bilinear expression; it is NOT
averaging the numerical solver residual.

Solver numbers are written as finite decimal strings via repr(float(value)).
The D8 raw track means the exact base-ten rational of that string, not the exact
binary floating-point value before serialization. The reconstructed track is
proposed entrywise under the supplied D8 policy and checked independently.
Source expressions never pass through rational reconstruction. A nonterminating
rational in the symbolic objective is explicitly unsupported by the D8 decimal
candidate format rather than silently rounded.

## The additional scalar-leaf order boundary

PEPit 0.5.1 creates its performance leaf tau during preparation. It need not be
scalar slot0. D6-D8 expect tau at slot0, followed by sampled function values in
D4 source storage order. D9 records both directions of a permutation of ALL
p+1 scalar leaves, including tau. This differs from D4's p sampled-value map.
Gram axes and actual prepared-constraint order are unchanged at this stage.

`TraceQ n k` retains the original exact row polynomials and objective, this
scalar permutation, the raw-decimal bound, all k ordered duals and the original
raw-decimal residual matrix. `checkTraceQ` checks the permutation, every moved
row, the moved objective, the unit <=0 conventions and the old D7 source audit.
`captured_row_eval` and `captured_objective_eval` use D4's full real evaluation
invariance for arbitrary real data, without a PSD or feasibility assumption.

The importer only fills coefficientwise diagonal zero rows in the full source
template. Every other full row must be represented exactly once in the actual
capture. D7 independently checks the coverage; D6 checks the performance link,
D5 the oriented rows, D4 order, D3 origin coordinates, and D2 the expected
profile. A producer's role labels do not bypass these mathematical checks.

## Binding numerical endpoints before reconstruction

`checkRawBindingQ` requires:

- raw bound equals the trace bound;
- raw objective equals the trace objective after the checked scalar permutation;
- raw implicit interpolation is empty;
- the COMPLETE ordered list of (row index, weight) equals
  [(0,w0),...,(k-1,w(k-1))]; and
- raw dualMatrix equals the trace's independent residual, on BOTH axes.

The exact PSD factors are not capture data. D1 synthesizes them separately for
each fixed endpoint matrix, and the old checker verifies them against that
matrix. Thus factor representation changes are not confused with numerical
changes of the recorded residual.

`checkCapturedQ` requires trace validity, raw binding and the old D8 reconstructed
joint acceptance. Raw mathematical validity is NOT a premise for reconstructed
validity. `checkCapturedRawQ` instead requires raw's own old D8 acceptance.
The new `checked_certificate` transmits the accepted reconstructed bound to the
same original Lean profile; the raw bridge transmits raw.bound independently.
No error-budget correction is added to an already exact accepted bound.

These statements bind submitted typed data to other submitted typed data and
to the formal profile. They do not authenticate PEPit, a solver, JSON parsing,
source bytes, package versions, timestamps, or metadata. Changing producer.mode
to 'live_solver_capture' does not change any mathematical acceptance predicate.
The report's capture hash is a canonical-JSON digest, not a provenance proof.

## Commands

Standard project verification (no optional solver dependency):

```bash
lake build LeanPEP && lake env lean tests/lean/smoke/V13D9SmokeTest.lean
```

Offline replay (requires only existing project Python dependencies):

```bash
python3 tools/import_pepit_proximal_gradient_capture.py \
  data/fixtures/pepit_capture/pg_three.json --expected-steps 3 \
  --output-dir /tmp/pg-capture-replay \
  --namespace LeanPEP.Imported.PGCaptureReplay --require-reconstructed-pass
```

Optional local capture, in a separate Python environment:

```bash
python3 -m venv /tmp/leanpep-pepit-env
/tmp/leanpep-pepit-env/bin/python -m pip install -r requirements-pepit-capture.txt
/tmp/leanpep-pepit-env/bin/python tools/capture_pepit_proximal_gradient.py \
  --steps 3 --output /tmp/pg-live-capture.json --solver CLARABEL
/tmp/leanpep-pepit-env/bin/python tools/import_pepit_proximal_gradient_capture.py \
  /tmp/pg-live-capture.json --expected-steps 3 --output-dir /tmp/pg-live-candidates \
  --namespace LeanPEP.Imported.PGLiveCapture
```

`--prepare-only` creates a symbolic capture with numerical=null. The offline
importer then reports source validity but produces no fake upper or numerical
Lean trace. It still requires the real PEPit package for preparation.

The optional `--require-reconstructed-pass` importer flag exits2 for a failing
exact reconstructed diagnostic, after retaining candidate files and reports.
Without that flag a well-formed but rejected candidate is retained and exit0
means conversion completed, NOT mathematical acceptance. Malformed input exits1.
Actual live reconstruction may fail even with source audit success: D8's simple
entrywise reconstruction is not a guaranteed feasibility recovery algorithm.

Generated `Capture.lean` contains DATA, not acceptance proofs. A local Lean
verification file must import it, assert `checkCapturedQ ... = true` with the
kernel, and invoke the generic actual-function bridge. Python diagnostics and
solver status never replace this step.
